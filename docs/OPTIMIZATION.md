## 产品定位与设计约束

三层结构：**时间层**（深黑夜色，记录疑问、回望札记）→ **想一想**（米白纸色，方向 / 节点 / 星图）→ **封存**（AI 凝练成信笺，写回时间层）。离线优先，可选云同步。

以下上限是刻意的产品立场，不是待修的缺陷，评估任何方案时都应视为约束（`components/zhihuo-model.ts:165-170`）：

| 约束 | 值 |
| --- | --- |
| 活跃空间 | ≤ 7 |
| 每空间方向 | ≤ 7 |
| 每空间节点 | ≤ 40 |
| 疑问 / 节点 / 回望札记字数 | 280 / 220 / 160 |

**当期总策略：不加新概念。** 先修掉会掉价的缺陷（已完成），再把已经付过成本的半成品收尾，然后把「信笺」这个最强资产往留存和展示两个方向放大。

### 数据信任冲刺（2026-07-27）

围绕「不能静默丢数据」完成了一轮端到端加固：

- **导出与导入统一为同一份规范快照。** 导入层同时兼容服务端导出的 snake_case 和现有客户端的 camelCase，补齐随记、节点关联、里程碑、方向判断与星图元数据；服务端导出文件现在可以校验后直接回导。
- **首次绑定改为先保全、后切换。** 选择云端数据时先为游客数据生成同步备份，确认云端拉取并落盘成功后才清理游客工作副本；失败时保留本地数据并停留在选择界面。上传本地数据的路径也会先备份。
- **阻止游客快照被空状态覆盖。** 已有有效游客快照遇到空、同步中或过期状态时不再被覆盖；工作副本与备份分开清理，保证切换账户后仍有恢复来源。
- **JSON 存储不再把损坏误判为空库。** 只有文件不存在才初始化空数据；解析失败、占用等错误会明确抛出。写入改为临时文件完成后原子替换，降低中断造成半文件的风险。
- **媒体缺失不再让整份导出失败。** 缺失附件会在导出结果中标记并返回警告，其他数据仍可正常导出；非“文件不存在”类读取错误仍会显式失败。
- **容器数据目录已持久化。** Docker Compose 新增 `/app/data` 命名卷，JSON 数据库和媒体文件不再只存在于容器可写层。

回归覆盖新增了完整思考快照与服务端导出格式的导入测试，并在 API 测试中加入「导出 → 校验 → 导入 → 再导出」一致性断言。
